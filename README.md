# PostgreSQL vs Solr full-text search

A small side project comparing full-text search in PostgreSQL (tsvector + GIN) and Solr on the same data:
how the queries look in each, how the results differ, and which one is faster.

## Data

We used the arXiv dataset from Kaggle: https://www.kaggle.com/datasets/Cornell-University/arxiv
(the metadata is CC0, so there are no licensing issues).

`arxiv-metadata-oai-snapshot.json` is several GB, so `prepare_data.py` takes a sample of 1M papers
and writes it to `data/arxiv.csv`. Records are picked by an MD5 hash of the id, so everyone gets the
same sample and the years are spread out fairly evenly. Each row also gets a `part` value (0-99).
If you want e.g. 10% of the data, take `part < 10` (the loading scripts have a `--max-part` option for this).

We don't keep author names, only the number of authors (`n_authors`), so there's no personal data in there.

Columns:

- `id` - arXiv identifier
- `title`, `abstract` - English text, this is what we search (abstracts are ~1000 chars on average)
- `main_cat` (~20 values, e.g. cs, math, astro-ph) and `sub_cat` (~150, e.g. cs.LG) - for filters, facets and GROUP BY
- `categories` - all categories of the paper (a list)
- `license`
- `year`, `pub_date` - date of the first version, used for sorting, ranges and boosting
- `n_authors`

## How to run

You need Docker (give it at least 5-6 GB of RAM) and Python 3.11+.

```bash
docker compose up -d      # postgres 17 on 5432, solr 10 on 8983
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

Then step by step:

```bash
# 1. download the json from Kaggle into data/ and turn it into a csv
python prepare_data.py data/arxiv-metadata-oai-snapshot.json --rows 1000000

# 2. postgres: table, COPY, tsvector column, GIN index
python load_pg.py

# 3. solr: collection with our schema + indexing
python solr_setup.py && python load_solr.py

# 4. queries and measurements
python run_queries.py     # queries, ranking, facets, highlighting
python bench.py           # timings
python extensions.py      # boost
```

Results end up in `results/` (.md and .json files). In Solr we turned off `update.autoCreateFields`
so it doesn't guess field types on its own. Documents are sent in batches of 5000 with a single
commit at the end.

The Solr admin panel is at http://localhost:8983/solr. Every Solr query is saved as a full URL in
`results/queries.md`, so you can just paste it into the browser.

## Queries

| | PostgreSQL (`to_tsquery('english', …)`) | Solr (`df=text_all`) | LIKE |
|---|---|---|---|
| Q1 - one word, any form | `galaxy` | `galaxy` | `LIKE '%galax%'` |
| Q2 - phrase + filter | `dark <-> matter` + `main_cat='astro-ph'` | `"dark matter"` + `fq=main_cat:astro-ph` | `LIKE '%dark matter%'` |
| Q3 - AND/OR with negation | `neural & (image \| speech) & !quantum` | `+neural +(image speech) -quantum` | 3× `LIKE` |

The SQL is in `sql/queries.sql`, and the scripts also print exactly what they ran.

## Solr schema

We set the flags so each field only has what we actually use:

| Field | Type | indexed | stored | docValues | multiValued | Why |
|---|---|---|---|---|---|---|
| `title`, `abstract` | text_en | ✓ | ✓ | - | - | we search them; stored so we can show them and highlight (hl) |
| `text_all` | text_en | ✓ | - | - | ✓ | copyField of title + abstract, only for searching, no need to store it |
| `main_cat`, `sub_cat`, `license` | string | ✓ | ✓ | ✓ | - | filters (fq), facets and sorting |
| `categories` | string | ✓ | ✓ | ✓ | ✓ | a paper can have several categories |
| `year`, `pub_date` | pint, pdate | ✓ | ✓ | ✓ | - | ranges, sorting, facet.range and boost |
| `n_authors` | pint | - | ✓ | ✓ | - | display only, we don't filter on it |
| `part` | pint | ✓ | - | - | - | technical field for picking a subset |

`text_en` is the analyzer from Solr's default config (tokenizer, stopwords, lowercase, possessive
's removal, Porter stemmer). Postgres with the `english` config uses the Snowball stemmer and has a
different, longer stopword list, which is why the hit counts differ a bit between the two.

## How we measured

Both systems get the same data and the same queries. One warm-up run, then the median of 5.
For Postgres we look at `Execution Time` from `EXPLAIN (ANALYZE, BUFFERS)`, for Solr at `QTime`.
We also measure the client-side time for both.

One catch with Solr is its result cache: running the same query again gives QTime ~0 ms, which
ruins the comparison since Postgres has no such cache. So we append `-id:nocache_<random>` to each
query. It doesn't change the results, but the cache doesn't kick in.

## Extra: boosting newer papers

We multiply relevance by `1 + (year - 1990) / 10` so newer papers rank higher. In SQL it's
`ts_rank_cd(...) * ...`, in Solr the `boost=` parameter in eDisMax. We compare the top 10 with and
without the boost, plus the average year in the top 10.

## Extended benchmarks: scaling, facets, duplicates and pagination

The extension compares LIKE, PostgreSQL FTS and Solr at 10%, 50% and 100% of the
dataset. It also compares two categorical facets and a range facet with SQL
GROUP BY, and tests duplicate handling (`collapse`) and deep pagination
(`start/rows` versus `cursorMark`).

The benchmarks use 500,000 unique arXiv papers from a
[Hugging Face mirror](https://huggingface.co/datasets/librarian-bots/arxiv-metadata-snapshot).
The metadata is listed under the CC0-1.0 license. Searches run against English
titles and abstracts; categories and publication years are used for filtering
and aggregation. The subsets contain 50,103, 250,183 and 500,000 documents.
Measurements include a warm-up run followed by five repetitions.

### Running the benchmarks (Windows / PowerShell)

Requirements: Python 3.11+, Docker Desktop with Linux containers and about 10 GB
of free disk space. The services use ports 15432 (PostgreSQL) and 58983 (Solr).

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-grade5.txt
.\.venv\Scripts\python.exe download_grade5.py --rows 500000
docker compose -p lab3grade5 -f docker-compose.grade5.yml up -d
.\.venv\Scripts\python.exe -u grade5.py all
.\.venv\Scripts\python.exe export_results.py
```

The downloader saves the data to `data/arxiv.csv`. Set `GRADE5_CSV` to use a
different location; gzip-compressed CSV files are also supported. For example,
an existing local setup can use `F:\Lab3Benchmark\data\arxiv.csv.gz`, with its
location specified in `.grade5.local.json`. To reuse prepared indexes on drive
F:, replace the standard Compose command with:

```powershell
$env:GRADE5_STORAGE_ROOT = 'F:/Lab3Benchmark'
docker volume create lab3grade5_zkdata5
docker compose -p lab3grade5 -f docker-compose.grade5.yml -f docker-compose.grade5.storage.yml up -d
```

`grade5.py` loads the data and runs the experiments. To run individual stages,
replace `all` with `scaling`, `facets`, `collapse` or `pagination`.
The substring comparison uses the case-sensitive `LIKE` operator.
The `scaling-like` stage reruns only the LIKE measurements on physical subsets
of the existing full table, preserving previous FTS and Solr measurements.
The scaling stage recreates the `grade5_arxiv` table and index. The other stages
require the full dataset, and the duplicate test uses a separate
`grade5_duplicates` index.

### Benchmark output

Raw measurements are saved to `results/grade5/`. `export_results.py` writes
tables (`wyniki.md`), a scaling chart (`skalowanie.png` and `.csv`), SQL queries,
Solr query URLs and a copy of the raw results (`raw/`) to `output/grade5/`.

Run `python package_grade5.py` to create `output/LAB3_czesc_5_0.zip` containing
the code and results, without the dataset.
